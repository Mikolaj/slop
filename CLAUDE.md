# CLAUDE.md

Every session starts here, in `~/slop`, where the repos worked on are checked out. This file holds what is common to most of them, binding in each mutatis mutandis --- in another maintainer's repo too, where only the coding-style rules yield, to the style of the file being edited. What only the current Claude models need telling is in `~/.claude/CLAUDE.md`; what is specific to one repo, or wanted by a human reading it, is in that repo's own `CLAUDE.md`. `tools/` here holds the tools the repos share and `docs/` the documents specific to none, the filed GHC and vector issues among them; the GHC to use is the one built in `ghc/`, described under the build tooling below. Examples are from horde-ad unless attributed.

## Coding style

- Haddocks are expected on all module headers and on functions/types in "major"/interface modules. Minor internal helpers get no haddocks; their comments, if any, must not be haddocks and may describe implementation details and go out of date --- don't treat every comment as authoritative documentation.
- Prefer assertions over comments to document invariants, unless that would be too verbose.
- `-fno-ignore-asserts` stays on in the cabal `common options` stanza, so failed `assert`s crash release builds too --- crash reports from released code can name assertions.
- Lens libraries are deliberately avoided; state lives in plain records (with record punning).
- GHC2024 is the default language; each project's default-extensions live in the cabal `common options` stanza. Projects normally set `StrictData` --- assume it unless the project's notes say otherwise.
- Formatting: 2-space indent, 80 columns, spaces not tabs, spurious whitespace avoided, spaces around arithmetic operators encouraged. Inline comments (`--`) are prefixed with exactly two spaces, unless indented to match other comments. Operators such as `(` and `,`, `<$>` and `<*>`, comment starts, etc. on consecutive lines either align or, if that would make lines too long, indent by 2 spaces from the previous indentation level. Generally, relax and stick to the style apparent in the file being edited.
- Put large, mechanical formatting changes in their own commit, separate from substantive changes.
- If hlint is still too naggy, adding more exceptions to `.hlint.yaml` is fine --- don't contort code to appease it.
- **Uniformity across analogous positions is itself a review tool.** Parallel code (e.g. the `Preserving`/`Shrinking`/`Padded` x `dKrn`/`dInp` x size families in the conv tests) and its comments should be identical modulo names and shapes; diffing analogous positions is how bugs surface, and a drifted one is normalized toward the cleaner form, not the first draft. One level up, things meant to be compared (benchmark variants, test cases) are designed as one-to-one counterparts --- measuring the same stage, differing only along the compared axis, adjacent in the output --- not accreted one probe at a time.
- **Order definitions as they are used, and let every summary span its whole subject.** Auxiliary definitions, do-bindings, list entries and top-level functions follow the order in which their consumers run, print or assert, wherever that order is deliberate or visible; an overview (module haddock, section comment) covers every member of what it describes, not the subset that existed when it was written. Both properties decay silently under accretion --- after adding to a set, re-normalize the whole set, not just the new member.
- **One meaning per name, and label deliberate asymmetries.** A letter or abbreviation keeps a single meaning per vocabulary (not `S`/`H` as both the pipelines and the gather orientations they produce, nor `c` as both concrete and contracted); and where uniformity is intentionally broken --- a counterpart deliberately absent, a definition that is a fixture rather than a candidate --- the site says so and why: an unexplained asymmetry looks like drift and costs a review round-trip.
- **Comments.** A substantial note that sibling sites would repeat with only names changed is stated once, at its canonical occurrence; tiny notes, by contrast, are repeated identically at every analogous position. Match the codebase's spelling and hyphenation (e.g. "poor man's", not "poor-man's") and keep terminal punctuation consistent across parallel clauses (don't end one with ";" and its sibling with "."). A comment must still match the code after refactors --- watch for notes invalidated by later changes. Leave pre-existing comments alone unless asked --- flag them instead.
- In tests, an expected crash may never fire due to laziness: an assertion or lookup error is swallowed if the offending value is never forced --- so force it, and under `StrictData` forcing to WHNF is enough, a strict constructor's fields being forced with it, which in horde-ad means WHNF fully builds an AST. Catch real assert failures with `Control.Exception.try`, rather than pattern-matching on output; the `blame`/`swith` details (from the `assert-failure` package) go to the trace output, not into the exception.
- **Prove a self-checking assertion is non-vacuous.** An invariant check --- e.g. verifying that scatter is the adjoint of gather via `sdot0 (sgather x f) y == sdot0 x (sscatter y f)` --- should be shown to actually fail when the property is deliberately broken, or it may be passing vacuously.
- Share the objective between a test and its benchmark via one exported helper, parameterized by what differs, so the benchmark provably measures what the test validates --- share code, not configuration.

## Working style

- **Scope discipline.** On an ambiguous request ("the *new* tests") take the narrower reading, do it, and flag the boundary with an offer to expand --- don't silently touch pre-existing code. Split unrelated work into separate PRs (e.g. convolution benchmarks + tests in one PR, the simplifier fix in another).
- **Verify before claiming done.** "Uniform" / "correct" / "passes" must rest on an actual line-by-line cross-check or a test run, not on the fact that it compiled; a claim about a touched file covers its pre-existing code too, so audit that as well.
- **Only/every/never claims must rest on repo-wide grep, and a superlative on SORTING the population, not on the file or the arms where the pattern was first noticed** --- analogous-variant families (`Preserving`/`Shrinking`/`Padded` x `dKrn`/`dInp`, the ranked/shaped/mixed op surfaces, the `Ops*` instances) make single-file generalization treacherous, and a 'first', 'only', 'widest' or 'lowest' is a claim about everything you did not look at, so derive it by ranking the whole set or scope it to the set you did rank ('the first on any binary still on disk'). One run shipped 'the first arms whose two statistics part in sign' --- no checker ranks a population, so it passed them all --- where two other pairs did it and ranking every pair took one command. The same discipline applies before concluding "this cannot happen here": grep for *every* site that could do it. Over prose rather than code, grep the unwrapped form --- `wrap80 --unwrap DOC` --- or the search is only as complete as the line breaks allow: a phrase the pattern needs whole stops matching the moment a wrap falls inside it, and the silence looks the same either way. That is not hypothetical: in horde-ad it cost `tools/check-doc-refs.py` two of README's backticked references, which is why that checker now processes the unwrapped form too.
- **Classify by the property you need, not by the proxy that greps easily.** Building LambdaHack's leader-conversion inventory, functions were bucketed by whether their *own* body performs an interactive wait --- mechanical, and wrong for the one whose wait sits in a helper it calls (`closeDirHuman`, whose `pickPoint` waits for it), which landed in the "harmless" bucket until re-read. The proxy is fine as a first cut if the write-up says which property it actually tested and treats its own count as a floor; a fixture or a plan that rests on the proxy silently inherits its blind spot, the same way misreading a three-disjunct predicate as two produced a fixture whose code path never fired.
- **A citation that resolves can still lie.** A `file:line` reference survives a refactor that moves the line: the file is long enough, so the check passes and the reference now points at whatever slid into that slot (in LambdaHack, a `CliMock` citation came to name a comment two hundred lines away). That is why the citation checker prints the snippet it found rather than only a verdict, why a document's verification stamp asserts the *reading* and not merely the resolution, and why the stamp names the newest commit touching a cited file --- the event that can invalidate the reading is exactly that file moving. The same holds at the HTTP level, where nothing here checks it at all: a URL returning 200 is not evidence that what the sentence attributes to it is still there --- horde-ad's CREDITS.md's MNIST provenance link now serves an empty directory index, all four named files gone, at the same 200 it always gave --- and the checkers fetch nothing, `URL_RE` matching only pinned `blob/<sha>/` permalinks and settling those against the commit rather than the network.
- **Prove a search non-vacuous before trusting its silence.** A grep that finds nothing has proved nothing until it is known to find something: run it first against a case known to be present. **This binds hardest when the search is checking your OWN fixes, and there the key matters as much as the non-vacuity:** a sweep keyed on the exact sentence you replaced cannot find a second site that words the same claim differently, so key it on the FIGURE or the claim and not on a phrasing --- one session verified twenty-five fixes that way, reported them all applied, and had left two sites standing that differed from the checked wording by two words. Plant a refuted claim in a copy and confirm the sweep flags it before believing a clean run of it. A tool is absent only when the invocation the check actually runs fails, tried as the check runs it: a failed `python3 -m pyflakes` once reported pyflakes missing while a `pyflakes` script on PATH would have run, and the checks went unrun for a day; today the script is gone and the module runs, so `command -v pyflakes` reports missing a tool that is there. Two wrong answers in one session came of skipping that (in LambdaHack: `grep '^??'` over colourised `git status` output, the git notes below, and concluding a note was absent from every document after grepping one of its phrasings). It is the rule already stated for assertions and for checkers, applied to searches --- and it reaches further than greps: a checker branch with no live control in a repository is a silent search too, which is why the tools under `tools/` name the branches their own recipes cannot exercise there. So is reading a file out of an archive: `tar xzOf PKG.tar.gz DIR/File.hs | grep -c NAME` prints 0 just as readily for a mistyped in-archive path as for an absent name, so grep something known to be in that file first --- this is how the orthotope version pin in `horde-ad/.claude/rules/performance-model.md` was established rather than guessed.
- **Commits should be clean and logical, not a diary of the work.** File-partition them, order them so exports precede uses, and fold a follow-up into the commit where its subject is logically born --- a correction to what you wrote an hour ago as much as a refactor, a document as much as code, and one `git commit --amend` for as long as that commit is not pushed to master branch --- rather than adding "add then move" churn. A second commit instead strands the first one's *message*, which goes on asserting whatever the fix retracted.
- **Never push, or open/force-update a PR, without an explicit go-ahead.** Permission to make a change is not permission to publish it.
- **Drafting GitHub-bound texts.**
  - One file per destination (issue, its design comment, PR description, upstream PR), staged in `docs/`, posted or not.
  - Keep the *design* implementation-ignorant and put measured results in the PR description.
  - Deliberate overlap between files is fine, to make each self-contained.
  - Don't attribute design intent to code that is merely generic ("assumes irregular indexing") --- state observed granularity and cost, not motives.
  - Prefer reference-style markdown links to keep the prose readable.
  - Wrapping is per destination: GitHub renders single newlines as hard `<br>` in issue/PR/comment *bodies* (though not in rendered `.md` files), so a draft meant to be pasted into an issue body, PR description or comment is kept *unwrapped* --- one long line per paragraph (blank line between paragraphs; tables, code fences, list items, reference-link definitions and `Co-Authored-By` trailers each still on their own line) --- so the browser soft-wraps it, and it is never re-wrapped to 80 columns, `wrap80 --unwrap -i` being what puts it in that form; a doc read as a repo file (e.g. README, committed notes) keeps that file's normal wrapping instead.
- **Links that cite source code --- in GitHub-bound texts and the reference documents --- must be GitHub permalinks pinned to a commit hash that is on `master`** (`...blob/<commit>/....hs#L12-L34`): branch-name and unpinned links drift or die when branches move, while a master hash survives rebases and stays verifiable --- the citation checker validates such permalinks against the pinned commit and then requires that commit to be an ancestor of `origin/master`, since `git show` resolves an unpushed or squashed-away commit from the local object database just as readily, and an unpushed commit's link 404s for everyone else, while a rebased-away one's may still resolve: GitLab served `6913545fd3` with no branch holding it (2026-10-19). Deliberately-living whole-file links (e.g. the README's `blob/master` pointers) are outside the rule, as are links to foreign repos.
- **A tracked file or a commit message cites no untracked file for what it says, unless Mikolaj approves the mention**: a scratch script or table, a plan, a handoff, a build tree. A clone has none of them and a cleanup can delete them, so the citation comes to point at nothing. State what the text needs from the file, or cite a tracked or published home; naming `/tmp/claude-1000` as the place to write scratch files cites nothing. *Why:* on 2026-10-18 a defect record cited a handoff and its scratch copy of a tool, as records written days before cited the untracked plan and scratch scripts, and two commits were rewritten when Mikolaj came to delete the files.
- **Name a filed GHC issue by its number, never by the local file that drafted it**: `GHC [#27742](https://gitlab.haskell.org/ghc/ghc/-/work_items/27742)` in every `.md` file but a body bound for that tracker, ruled 2026-09-17 so that a reader follows the reference rather than searching for it, the bare URL in place of the number where a link cannot render --- a code comment, and a code block inside a document --- `GHC #27742` in a commit message and in chat, and a bare `#27742` only inside that tracker-bound body, which is the one place it autolinks. Two other spellings stay and are exceptions rather than drift: the header line of a `docs/ghc-issue-*.md`, which names its own work item and its siblings' in the tracker's own noun and sits above the filed body rather than in it, and a third-party item in a sentence that has already said which tracker it is on. What no exception covers is a bare filename standing where the issue belongs. The `GHC` is what separates it from horde-ad's own `#123`, so it is required wherever the surrounding text has not already established which tracker is meant; a first mention carries the full form and later ones in the same document may shorten to the number, adjectivally included. `docs/ghc-issue-linear-regalloc-order.md` is a path in this repo --- meaningless to a reader anywhere else, and to upstream most of all --- so the file stays as the filed record, named as a file where a reader should open one and never standing in for the issue. This binds every repo's documents, which reach those files by a path that resolves only in `~/slop`.
- **State mathematical properties in the code's surface notation, not abstract math** (in docs and comments alike). Write the gather/scatter adjoint law as `sdot0 (sgather x f) y == sdot0 x (sscatter y f)`, not `<gather x, y> = <x, scatter y>`: keep the index function `f` explicit rather than hidden in the operator name, and put quantifiers first (*for all `f`, `x`, `y`*). It reads in the vocabulary of the code and keeps the shapes checkable.

## Sandboxing on the dev machine (outer wrapper + inner sandbox)

Claude Code sessions on Mikolaj's machine run inside an outer bwrap sandbox wrapper (PID 1 is `bwrap`), beyond Claude Code's own (inner) sandbox. Sessions start in `~/slop`, which holds the repositories worked on but `~/.claude`, so a sandboxed write lands anywhere in them; what follows about writing outside the working directory and about sibling checkouts bites on an edit to `~/.claude`, on a repository outside `~/slop` and on the read-only paths the first bullet names, every repository's `.git/config` among them (measured 2026-10-19), and the inner sandbox's placeholders land in `~/slop`'s own root rather than a repository's. Current state and its implications:

- Run `git` writes and `gpg` unsandboxed --- the inner sandbox mounts `.git/config` and `~/.gnupg` read-only. A sandboxed command may write `~/.cabal`, which `sandbox.filesystem.allowWrite` in `~/.claude/settings.json` has named since 2026-10-19. The inner sandbox's network filter refuses every host no settings source allows, and the same file's `sandbox.network.allowedDomains` allows only GitHub's hosts, GHC's GitLab and Hackage (measured 2026-10-19): a call needing any other host lists it in the Bash call's `allowed_domains` or runs unsandboxed. `git checkout -b` / `branch -f` fail to lock the config, though the ref often moves anyway --- verify refs afterwards. GPG signing (`commit.gpgsign` is on) fails sandboxed and works unsandboxed, so never fall back to `--no-gpg-sign`; SSH pushes likewise work only unsandboxed.
- **Anything outside the working directory refuses a *sandboxed* Bash write and accepts an unsandboxed one**, the read-only HOME mounts and the sibling checkouts alike: `~/.claude/projects` and, from a session started in horde-ad, `../orthotope` were measured in all four cells and do not differ, whatever a mechanism story suggests. The Write and Edit tools reach both regardless. So there are always two routes, and the choice is worth real tokens: Edit for a few lines, an unsandboxed `python3` splice for anything structural, a move otherwise shipping the block twice through Edit and costing tens of thousands of tokens where a script costs hundreds. Expect the wrong half to be learned by accident --- a session meeting `Read-only file system` from a *sandboxed* script concludes Bash cannot write there at all and reaches for Edit ever after. **And it misreports MOUNT FLAGS and not only what a write gets**: a path the inner sandbox will not let you write is reported `ro` by a sandboxed `mount` or `findmnt` and `rw` by an unsandboxed one, and what it presents is a read-only view with a writable one STACKED where it permits writes, so `findmnt -T` names the target TWICE for a path you may write and ONCE, `ro`, for one you may not --- which is the cheapest sandboxed test of whether a write will land, but for a checkout inside `~/slop`, shown ONCE, `ro`, and taking the write all the same (2026-10-20). `findmnt` reports a sibling checkout as `ro,nosuid,nodev,relatime` sandboxed where the real mount is `rw`. So a verdict about what any mount permits is the sandbox's unless it was taken unsandboxed; met 2026-09-21 on a tmpfs at `micro-regime3/hugebin`, where the sandboxed reading would have indicated a run could not launch from a mount that was in fact writable.
- **A blocked write runs nothing at all, and under a typed `&` --- which is why a session does not type one --- leaves the command's fate unreadable.** Measured both ways: a simple command's redirections are checked before exec, so `cmd > blocked.log` and `nohup cmd > blocked.log` report the failure and run nothing at all, the command's own side effects included; while a pipeline fails only at its consumer --- `tee` opens its file itself, after the shell has forked --- so `cmd | tee blocked.log` reports the error and `cmd` keeps going. Backgrounded with a bare `&` that survivor is detached and invisible, and the launch looks as if it never happened --- two copies of a benchmark once ran side by side, contending, because one was read that way. The harness's own background mode reports the job's exit whatever the redirect did, and a pipeline whose consumer died still shows as running.
- Paths the wrapper blocks report "No such file or directory", not "Permission denied". If a path outside the repo seems missing --- especially one documented as expected, like horde-ad's `../ox-arrays` sibling checkout --- suspect the wrapper rather than recording the path as absent. `dangerouslyDisableSandbox` bypasses only the inner sandbox, never the wrapper. `tools/check-doc-refs.py` encodes the same rule: it resolves sibling checkouts when present and *stops* (exit 2) when one is not, rather than falling back to a weaker check, so a BLOCKED run means the check did not happen, not that it passed. **The complement is worse, because it is silent: a path CREATED under an unmounted parent succeeds and is invisible outside.** `mkdir ~/r/orthotope-pr` works, reads back, builds, and does not exist for Mikolaj --- so what looks like a delivered directory is a phantom of this session's mount namespace. The trap has teeth where a real path and a phantom one are written in the same command: `git worktree add ~/r/orthotope-pr BRANCH` puts the worktree registration and the commits in the MOUNTED `.git`, so the objects and the ref are real and survive, while the working tree is not there at all --- and the registration then makes git refuse to check that branch out anywhere, for a directory nobody can see. Prefer a path inside a mounted checkout, and where one is not available say what was written and where rather than reporting a directory delivered (2026-08-30).
- **Where a sibling checkout and the released version it tracks disagree, the checkout wins.** It is ahead of the release and actively worked on, not stale, so read it for what upstream *is*: `orthotope` sat at 0.1.8.0 plus unreleased commits rewriting the very strided fallback the gather cost bullet in `horde-ad/.claude/rules/performance-model.md` describes, which would have been recorded as current had the release been treated as the authority. The cabal store provides what the checkout cannot: what to read when the wrapper hides the mount, and whether a *version-sensitive name* a document pins is really in the release the build plan resolves. A note resting on upstream code the checkout has since changed says so, and names what to re-measure when that work lands.
- The wrapper mounts a fixed set of HOME paths, curated per-path rather than per-directory, plus whatever repo checkouts it was launched with, skipping in silence any that do not exist --- which is where the previous bullet's "No such file or directory" comes from. The fixed part can be relied on; the checkouts are what varies from session to session, `~/r` having at times held only the current repo, so verify a sibling at the moment it matters rather than inferring it from habit. That an entry is visible still says nothing about how much of its contents is: `~/.ssh` carries public material only.
- Sandboxed `ls` shows phantom dotfiles in the working directory that don't exist on the real filesystem, and `~/slop`'s `.gitignore` keeps them, with the `.claude/` placeholders, out of `git status`. HOME is *not* remapped to the repo root, whatever the names suggest: the inner sandbox bind-mounts `/dev/null` over eleven names in the directory it was launched in, once per Bash call. So one path stats three ways --- a character device 1,3 mode 666 from inside the call holding the mount, a regular empty file mode 444 (the placeholder that mount needs) from any other mount namespace while that call is live, whether an unsandboxed command or a second concurrent sandboxed one, and absent when no call is running. The form follows vantage and timing, not the checkout, and a sibling checkout gets none of them at all --- which is the half measured from horde-ad, that repo having been the sibling when the three states were established. A session rooted in the directory is the one that can confirm the device state; the mode-444 reading horde-ad's `CLAUDE.md` used to carry is what the account predicts a second concurrent call, or an unsandboxed one, would return. Ignore them; verify with an unsandboxed command before deleting any. The eleven are `.bashrc`, `.gitconfig`, `.gitmodules`, `.mcp.json`, `.profile`, `.bash_profile`, `.zshrc`, `.zprofile`, `.ripgreprc`, `.idea`, `.vscode`, worth listing because two of them are names a repository could legitimately carry and would then appear empty rather than missing. That is enough to move a checker's verdict: a backticked `.mcp.json` in this file makes `tools/check-doc-refs.py` resolve it from a session rooted here and fail it from one rooted elsewhere, or from an unsandboxed run, until an entry in `tools/doc-refs-allow.txt` settles the answer everywhere. The same masking covers the `.claude/` entries a session must not write, settings.json among them though `~/slop` carries none, and there it reaches Claude Code itself: its `--debug` log records a *Detected change to* that path and reloads every settings source on it --- CA certificates re-read, the sandbox configuration re-derived, all permission rules replaced. It has rules to replace: the user settings allow `Edit(~/.claude/CLAUDE.md)`, and `~/slop/.claude/settings.local.json`, a real file, allows `Read(//home/mikolaj/.claude/**)`; whether a reload loses them has not been measured (2026-10-19). No project `sandbox` block competes with the user-level one carrying `enableWeakerNestedSandbox`; adding one would give the reload that to lose as well. The same reload reads `.mcp.json` at length zero and logs it as invalid JSON, which costs nothing while no such file exists --- but a real one here would load at startup and then be read as empty on the first reload after any Bash call, dropping its servers mid-session.
- The inner sandbox is in its own PID namespace, so `ps` there lists only the session's own processes and `kill -0 <pid>` is not a liveness test: it fails for a process that is running fine, and an `until ! kill -0 ...` waiter therefore returns at once. That reported a still-running build as finished once. Poll unsandboxed, or watch the thing's output file rather than its pid --- except that a file whose creation the sandbox blocked stays absent whether or not the process is running (sandboxing notes above), so there its absence proves nothing and only the unsandboxed process list settles it.
- System state under wrapper-hidden paths cannot be inspected from inside a session; such diagnosis must be done by Mikolaj in a plain terminal. Most of `/etc` is in that class, the wrapper carrying `resolv.conf`, `hosts`, `ssl`, `passwd`, `group`, `alternatives` and `fonts` and no more, so `/etc/apparmor.d` here is an instance of one rule rather than a separate surprise, and the next `/etc` path to come back missing is predictable. The last two were added on 2026-08-10 after a session traced failures to them, `/etc/alternatives` being what the shell-tooling notes below rest on.
- The nested inner sandbox works only because three things hold; if sandboxed commands start failing at startup, check these first:
  - the Ubuntu AppArmor userns restriction is off (`kernel.apparmor_restrict_unprivileged_userns=0`, no `bwrap-userns-restrict` profile);
  - the wrapper mounts the repo read-write;
  - `enableWeakerNestedSandbox: true` is in effect --- inherited from the `sandbox` block of the user-level `~/.claude/settings.json` (a project `sandbox` block wholesale replaces the user-level one --- settings objects don't deep-merge --- so a project that defines one must repeat the flag).

## Git and GitHub in sessions

- `gh` is authenticated only unsandboxed, and sandboxed it degrades rather than fails, which is the trap: its real token is in the keyring, out of the inner sandbox's reach, so it falls back to the read-only `~/.config/gh/hosts.yml`, whose token is invalid, and proceeds unauthenticated. Measured both ways --- 60 requests an hour against 5000, and `/actions/jobs/<id>/logs` returning 403 "Must have admin rights to Repository" where an unsandboxed run returns the log. The network itself is there sandboxed, a plain `curl` to api.github.com giving 200, so what is missing is the credential and not the route, and `gh auth status` names it outright. Run `gh` unsandboxed, alongside `git` writes and `gpg`. `glab` differs on both counts: its token sits in a readable config file, so it works sandboxed too, but only for the host named by `GITLAB_HOST` (gitlab.haskell.org here) --- `glab auth status` lists gitlab.com alone even while the other host's credential is present and working. So GHC's tracker is read through `glab` --- `glab api 'projects/ghc%2Fghc/issues?search=...&state=all'`, `glab issue list -R ghc/ghc --search ...` --- and never through `curl` with a pasted token: on 2026-09-06 a session handed a token reached for `curl` and an inline one-liner first, lost a round to quoting, and had `glab` logged in the whole time.
- `git status --short` is colourised even through a pipe --- the bytes are `^[[31m??^[[m path` --- so `grep '^??'` silently matches nothing. Use `git status --porcelain`, which is defined as machine-readable and is never colourised.
- A `git stash pop` chained after a `git stash push -- <path>` is a trap, because the push can succeed having saved nothing: given a pathspec with no local changes it prints "No local changes to save" and exits 0, so the pop then takes the *top of the stash stack* --- hundreds deep in horde-ad, holding parked branch work --- restores that into the tree and drops the entry. Park a file by copying it aside, not by stashing it.
- Interactive git is unavailable (tool commands run without a TTY, so editor and prompt loops hang): no `rebase -i`, no `add -i`. Rewrite history with `git reset --mixed <base>` + re-`add`/`commit` per file group, reusing messages via `git commit -C <hash>` / `-F <file>`.
- Amending HEAD costs one `--amend`, and squashing a follow-up into it a `git reset --soft HEAD~1` first; a non-HEAD commit is the expensive case (no `rebase -i`). Edits that replace text in files the commit already has, up to any later commit deleting that text, go through `tools/rewrite-fold.py`, which rebuilds the branch tree by tree without conflicts, rewords commits where asked, and prints the new tip for `tools/rewrite-check.py` to check before a guarded reset moves the branch; anything else is saved as a patch, `git reset --hard <target>` (spares untracked files), applied and `--amend`ed, and the successors `git cherry-pick`ed (conflict-free when they don't touch the amended files). Update recorded hashes either way.
- The repo root accumulates many untracked scratch files (`log*`, `*.prof`, `cabal.project.local.bkp*`, `.emacs.desktop*`, etc.); leave them alone and never `git add` them wholesale --- which means naming the paths on every `git add`, since `-A` over a directory takes every one of them. **And read the diffstat of the commit you just made**, because nothing else shows it: one `git add -A` in orthotope's micro-regime3 committed 79 scratch files, 176632 insertions and five 32 MB binaries, and `git status` then reported CLEAN, the files having been absorbed. It was found three hours later in the same session, by a review of the diff's SHAPE noticing 83 changed files where four were expected; no pass between saw it.

## Build and shell tooling in sessions

- `pkill -f PATTERN` matches the issuing shell's own command line, which contains the pattern, so it kills the shell that ran it --- the tool call comes back with exit 144 and nothing else, twice mistaken here for the command failing. Take pids from `ps` and `kill` those instead. Sandboxed calls are spared that, by accident rather than by design: Claude Code's shell snapshot shadows `pkill` with a function that refuses any pattern whose `pgrep` hit equals `$CLAUDE_PID`, and in the inner sandbox's PID namespace the issuing shell is itself PID 2 --- the number the CLI holds in the wrapper's namespace --- so what fires is a collision between two namespaces rather than recognition of the CLI. Don't lean on it: unsandboxed, where the shell carries some other number, the same command still killed its own shell at exit 144. **The property belongs to any matcher run over your own command line, not to those two commands**, so a waiter hand-rolled out of `ps` inherits it whole: `pgrep -f` self-matches identically and, being shadowed by nothing, fails more quietly --- an `until ! pgrep -f PATTERN` waiter finds its own shell, so the condition never goes false and it waits until something kills it, where `pkill` at least ends the call loudly --- and `until ! ps -eo args | grep -q PATTERN` is the same waiter with the shadowing gone and no name to recognise it by, hung in orthotope on 2026-09-01 until it was killed by pid. Wait on a file's contents instead, and where the harness wakes you when a job ends, set no waiter at all. That is a job the HARNESS backgrounded: a typed `&` detaches just as well, registers nothing and wakes nobody (2026-09-04). A pattern the matcher cannot match, `'seq 1 [6]0'`, dodges both --- but only its own occurrence: a kill-then-relaunch script still dies through the literal name in its later launch line, measured in LambdaHack at exit 144 unsandboxed and meeting the refusal above when sandboxed, so kill and relaunch go in separate calls.
- Commands managed by `update-alternatives` --- `awk`, `cc`, `which`, `vi`, `pager` and the rest --- resolve in sessions since the wrapper began mounting `/etc/alternatives` (2026-08-10); before that every `/usr/bin` symlink pointing there dangled. The fix is that one mount and not a shim per command: the `~/.local/bin/awk -> mawk` link that had stood in for one of them is removed, and a retargeted alternative now reaches a session on its own. `hlint` and `stylish-haskell` are on PATH (via `~/.cabal/bin`) and work in-session, sandboxed included.
- `grep` is not the binary on PATH but a bash function Claude Code writes into its shell snapshot, routing to a ugrep (7.5.0) embedded in the `claude` executable; `find` is shadowed the same way, by bfs. A function shadows every PATH entry and `\grep` does not escape one, backslash suppressing aliases rather than functions, so `command grep` --- GNU grep, at `/usr/bin/grep` --- is the way back; the shims are not exported, so a Makefile recipe or a `python3` subprocess already gets the real thing. Three of the differences are silent: a recursive search skips gitignored paths, `--ignore-files` being injected, so a walk over the repo passes over `log*`, `dist-newstyle` and `*.prof`; binary files are skipped (`-I`), so `-c` prints nothing and exits 1 where GNU prints a count and exits 0; and `-r` output paths lose their leading `./`. The regex dialect is *not* one of them --- GNU BRE's `\|` and its siblings behave identically --- so an alternation that matches nothing means `-E`, `-P` or `rg`, where `\|` is a literal pipe in any grep; blaming that on ugrep put a fabricated machine fact one approval away from this file. What is ugrep's own: `-P` means PCRE2, it can reject a regex outright with `exceeds complexity limits` where GNU grep would run it, and on the one-line-per-paragraph documents here a bounded-repeat alternation can instead run for minutes --- reach for python when a pattern gets involved. The checkers under `tools/` are unaffected: they match with Python `re` rather than with whatever `grep` resolves to. Only `check-doc-refs.py` shells out to `git grep` at all, and only for its flag-usage check.
- To combine several tasty `-p` patterns, tasty requires awk-style syntax: `-p "/foo/ || /bar/"`.
- A tasty `-p` pattern matches by *containment* and cannot be anchored, in two forms that fail differently. A pattern of nothing but alphanumerics, `.`, `_`, `-` and spaces is taken whole as a literal substring and never parsed --- the ordinary form, `-p "4S"` --- while anything else goes to the awk grammar, where an ERE token `/foo/` recognizes no special characters either and `$NF` is the test's own name. So an anchor fails two ways and only one is loud: `-p "^detSquare"` is rejected, "is not a valid pattern", where `-p "/^detSquare/"` is accepted and silently selects nothing. `-p '$NF == "detSquare9"'` is the exact-match form. The consequence is silent, and biting wherever names are numbered: `-p "gatherNested1"` selects two tests, `gatherNested1` together with `gatherNested12` --- so a filter believed to name one test quietly runs two, and a count taken through it moves for reasons nobody sees. Mint a marker by listing before the series exists: the same `--list-tests` reports a count for a marker that does exist, which is what keeps the check from passing vacuously.
- Criterion (the benchmark suites) filters differently and does *not* accept that syntax --- it has no `-p`: bare positional args are **prefix** patterns on the full `group/bench` path, and `-m glob`/`-m pattern`/`-m ipattern` switch the match mode (e.g. `--benchmark-options='-m glob "*/S-exec"'` to pick a bench across groups, or a bare `--benchmark-options='cnn-24x24'` prefix).
- **A verification command must not be piped, and must not sit behind `&&` either.** A shell pipeline exits with its *last* command's status, so `cabal test CAFlessTest --enable-optimization | tail -40` reports `tail`'s success whatever the run did --- and the session harness then reports "exit code 0", which looks exactly like a pass. Redirect to a file and echo `$?` instead. It bites harder in horde-ad than in most places: warnings are deliberately ignored there (its standing checks), so the exit status is the whole signal and the pipe is precisely what discards it. The failure is silent by construction and survives every other check, which is why it belongs here rather than in one tool's recipe --- `tools/check-plan-citations.py`'s non-vacuity recipe already tells its own reader to check the status without a pipe, having once read five successes that were four refusals. **The `&&` chain is the same defect wearing a different construct**, and it fails one step earlier: a status read placed after `&&` does not run at all when something before it fails, so a trailing `||` fallback fires and looks like the verdict --- `git commit ... && git log ... && git status ... || echo "(tree clean)"` printed *(tree clean)* on 2026-09-03 with the commit refused and three files still staged. Put the check in its own call, or read the state directly afterwards; a fallback that can print a result for a command that never ran is not a check.
- **A comment line that begins with the word `shellcheck` is read as one of shellcheck's own directives**, so a note *about* the tool fails the whole file at SC1072/SC1073 ("Couldn't parse this shellcheck directive") rather than being ignored --- rephrase so the word does not start the line.
- GHC emits warnings only on *recompilation*: a cached, up-to-date build can hide warnings (e.g. `-Wredundant-constraints`) that a full rebuild would surface --- don't infer "no warnings" from a clean second build. Optimization level hides a second class: `-Wmissed-specialisations` fires only when the specialiser runs, so a from-scratch `-O0` build reports none of it, and `--ghc-options=-fforce-recomp` does not help --- cabal reports "Up to date" and compiles nothing, since the flag doesn't reach its staleness check. A released GHC's recompilation check misses a change of any setting that carries a *value* --- `-fllvm`, the inliner thresholds and `-fproc-alignment` among them (GHC [#27667](https://gitlab.haskell.org/ghc/ghc/-/work_items/27667), fixed in the default GHC above) --- so an A/B that toggles one of those measures nothing unless it forces the rebuild. To force a genuine rebuild, build into a fresh `--builddir`, which leaves the existing artifacts alone.
- **`-keep-s-files` keeps nothing under a build that names `-pgma`**: a fresh `--builddir` of orthotope's `micro-regime3` under GHC HEAD `10.1.20260918` held no `.s` at all after one (2026-09-22), so the assembly a shim plans over is captured by wrapping `-pgma` in a script that copies each `.s` argument aside and then runs the shim.
- **A binary under `dist-newstyle` can silently predate the tree, so check before measuring it.** `cabal build convVjpBench --dry-run` names what it would rebuild and why ("file X changed"), which is the cheap way to know the executable about to be timed is the one the source describes. Reverting an edit without rebuilding cost two wrong conclusions in one session: the binary still carried the reverted code, and the extra startup work it did was read as a property of the suite, contradicting an earlier measurement that had been right all along.
- Keep one set of cabal flags across a session --- changing flags (e.g. toggling `--enable-optimization` or `--enable-profiling`) forces a full rebuild of the local packages, though each flag set's dependency builds stay cached in the store. Pass such flags on the command line rather than editing `cabal.project.local`.
- The `/tmp` scratchpad is wiped by a machine restart, and the wrapper's tmpfs over `/tmp` also hides it from Mikolaj's own shell --- put anything that must survive (patches, notes) or that he has to run or open himself (a `! bash foo.sh` script, a diff to review) in the repo tree instead, with a note to delete it afterwards; binaries just get rebuilt. Handing over a scratchpad path yields "this file doesn't exist" and a wasted round trip. `$TMPDIR` is `/tmp/claude-1000` only under the inner sandbox; an unsandboxed command uses `/tmp`, so a file one seat writes to `$TMPDIR/foo` is missing from the other's. Spell scratch paths out as `/tmp/claude-1000/...` in both seats: that directory is writable in both.
- Exact dependency sources are always available: unpack `~/.cabal/packages/hackage.haskell.org/<pkg>/<ver>/` matching `dist-newstyle/cache/plan.json`.
- `.github/workflows/haskell-ci.yml` is generated by `haskell-ci` from the `.cabal` file --- regenerate it (`haskell-ci regenerate`) rather than hand-editing. Anything the generator does not produce belongs in `cabal.haskell-ci`, not in the generated file: a plain field where one covers it (`apt:` for extra system packages, `run-tests:`, ...), and `github-patches:` for a diff reapplied on every regeneration. A hand edit left outside that config is not merely fragile, it disappears *silently* on the next regenerate --- which is what a rewritten `tests` step and a whole `benchmarks` step in horde-ad were exposed to, a plain regenerate dropping both without a word, until the first moved into the patch and the second into a hand-written workflow of its own. After changing the config, regenerate twice and compare: a patch that applies cleanly once can double-apply. (In LambdaHack the same role is played by an `apt:` entry, `libsdl2-ttf-dev`, which that repo nearly lost the same way.)
- Toggle-based A/B builds: make a rule's guard unsatisfiable (e.g. `sigmaL /= sigmaL`), build and copy the binary aside, restore + rebuild + copy again, then run the two preserved binaries in interleaved pairs (no rebuild between A and B); an edited `Core` module rebuilds in ~10 min.
