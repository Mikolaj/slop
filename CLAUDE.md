# CLAUDE.md

Every session starts here, in `~/slop`, where the repos worked on are checked out. This file holds what is common to most of them and binds in each mutatis mutandis, in another maintainer's repo too, where only the coding-style rules yield, to the style of the file being edited. What only the current Claude models need telling is in `~/.claude/CLAUDE.md`; what is specific to one repo, or wanted by a human reading it, is in that repo's own `CLAUDE.md`. `tools/` here holds the tools the repos share and `docs/` the documents specific to none, the filed GHC and vector issues among them. The GHC to use is the one built in `ghc/`, described under the build tooling below. Examples are from horde-ad unless attributed.

The incidents and measurements behind a bullet are in `CLAUDE-why.md` beside this file, one entry per bullet under its lead words, and those of the sandbox, `gh`, `pkill` and `grep` bullets in `docs/session-machine-facts.md`. Neither is loaded: read a bullet's entry before changing or removing the bullet, and when what you meet differs from what the bullet says; record a new incident there, not here.

## Coding style

- Haddocks are expected on all module headers and on functions/types in "major"/interface modules. Minor internal helpers get no haddocks; their comments, if any, must not be haddocks and may describe implementation details and go out of date, so don't treat every comment as authoritative documentation.
- Prefer assertions over comments to document invariants, unless that would be too verbose.
- `-fno-ignore-asserts` stays on in the cabal `common options` stanza, so failed `assert`s crash release builds too: crash reports from released code can name assertions.
- Lens libraries are deliberately avoided; state lives in plain records (with record punning).
- GHC2024 is the default language; each project's default-extensions live in the cabal `common options` stanza. Projects normally set `StrictData`: assume it unless the project's notes say otherwise.
- Formatting: 2-space indent, 80 columns, spaces not tabs, spurious whitespace avoided, spaces around arithmetic operators encouraged. Inline comments (`--`) are prefixed with exactly two spaces, unless indented to match other comments. Operators such as `(` and `,`, `<$>` and `<*>`, comment starts, etc. on consecutive lines either align or, if that would make lines too long, indent by 2 spaces from the previous indentation level. Generally, relax and stick to the style apparent in the file being edited.
- Put large, mechanical formatting changes in their own commit, separate from substantive changes.
- If hlint is still too naggy, adding more exceptions to `.hlint.yaml` is fine: don't contort code to appease it.
- **Uniformity across analogous positions is itself a review tool.** Parallel code (e.g. the `Preserving`/`Shrinking`/`Padded` x `dKrn`/`dInp` x size families in the conv tests) and its comments should be identical modulo names and shapes. Diffing analogous positions is how bugs surface, and a drifted one is normalized toward the cleaner form, not the first draft.
  - **Things meant to be compared (benchmark variants, test cases) are designed as one-to-one counterparts:** measuring the same stage, differing only along the compared axis, adjacent in the output, not accreted one probe at a time.
- **Order definitions as they are used, and let every summary span its whole subject.** Auxiliary definitions, do-bindings, list entries and top-level functions follow the order in which their consumers run, print or assert, wherever that order is deliberate or visible. An overview (module haddock, section comment) covers every member of what it describes, not the subset that existed when it was written. Both properties decay silently under accretion: after adding to a set, re-normalize the whole set, not just the new member.
- **One meaning per name, and label deliberate asymmetries.** A letter or abbreviation keeps a single meaning per vocabulary: not `S`/`H` as both the pipelines and the gather orientations they produce, nor `c` as both concrete and contracted. Where uniformity is intentionally broken (a counterpart deliberately absent, a definition that is a fixture rather than a candidate), the site says so and why: an unexplained asymmetry looks like drift and costs a review round-trip.
- **Comments.** State once, at its canonical occurrence, a substantial note that sibling sites would repeat with only names changed; repeat a tiny note identically at every analogous position. Match the codebase's spelling and hyphenation (e.g. "poor man's", not "poor-man's") and keep terminal punctuation consistent across parallel clauses (don't end one with ";" and its sibling with "."). A comment must still match the code after refactors: watch for notes invalidated by later changes. Leave pre-existing comments alone unless asked, and flag them instead.
- **In tests, force the value an expected crash depends on:** an assertion or lookup error is swallowed if the offending value is never forced. Under `StrictData` forcing to WHNF is enough, a strict constructor's fields being forced with it, which in horde-ad means WHNF fully builds an AST. Catch real assert failures with `Control.Exception.try`, rather than pattern-matching on output; the `blame`/`swith` details (from the `assert-failure` package) go to the trace output, not into the exception.
- Share the objective between a test and its benchmark via one exported helper, parameterized by what differs, so the benchmark provably measures what the test validates: share code, not configuration.

## Working style

- **Scope discipline.** On an ambiguous request ("the *new* tests") take the narrower reading, do it, and flag the boundary with an offer to expand; don't silently touch pre-existing code. Split unrelated work into separate PRs (e.g. convolution benchmarks + tests in one PR, the simplifier fix in another).
- **Verify before claiming done: "uniform", "correct" or "passes" must rest on an actual line-by-line cross-check or a test run, not on the fact that it compiled, and an only, every or never claim on a repo-wide grep.** A claim about a touched file covers its pre-existing code too, so audit that as well. Analogous-variant families (`Preserving`/`Shrinking`/`Padded` x `dKrn`/`dInp`, the ranked/shaped/mixed op surfaces, the `Ops*` instances) make generalizing from the file or the arms where a pattern was first noticed treacherous.
  - **A superlative rests on sorting the population.** A "first", "only", "widest" or "lowest" is a claim about everything you did not look at: derive it by ranking the whole set, or scope it to the set you did rank ("the first on any binary still on disk"). No checker ranks a population.
  - **Before concluding "this cannot happen here", grep for every site that could do it.**
  - **Over prose rather than code, grep the unwrapped form** (the wrapping bullet of the user-scope `CLAUDE.md`).
- **Classify by the property you need, not by the proxy that greps easily.** Bucketing functions by whether their own body performs an interactive wait is mechanical, and wrong for the one whose wait sits in a helper it calls. The proxy is fine as a first cut if the write-up says which property it actually tested and treats its own count as a floor; a fixture or a plan that rests on the proxy silently inherits its blind spot.
- **A citation that resolves can still lie: cite code by a text anchor, or by a permalink pinned to the tree a sentence describes.** A `file:line` reference survives a refactor that moves the line: the file is long enough, so the check passes, and the reference now points at whatever slid into that slot. A moved line keeps a text anchor and a rewritten one breaks it loudly. The citation checker refuses a line number outright (since 2026-10-21) and prints the line it found rather than only a verdict, an anchor that resolves being no proof that its line still says what the sentence needs.
  - **A URL returning 200 is not evidence that what the sentence attributes to it is still there,** and nothing here checks it: the checkers fetch nothing, `URL_RE` matching only pinned `blob/<sha>/` permalinks and settling those against the commit rather than the network.
- **Prove a check non-vacuous before trusting its silence: an assertion, a checker, a search.** Show that a self-checking assertion (e.g. that scatter is the adjoint of gather, `sdot0 (sgather x f) y == sdot0 x (sscatter y f)`) actually fails when the property is deliberately broken, or it may be passing vacuously. A grep that finds nothing has proved nothing until it is known to find something: run it first against a case known to be present.
  - **A sweep that checks your own fixes is keyed on the figure or the claim, not on a phrasing.** Keyed on the exact sentence you replaced, it cannot find a second site that words the same claim differently. Plant a refuted claim in a copy and confirm the sweep flags it before believing a clean run of it.
  - **A tool is absent only when the invocation the check actually runs fails, tried as the check runs it.** `python3 -m pyflakes` and a `pyflakes` script on PATH have each been there without the other, so `command -v pyflakes` settles nothing.
  - **A checker branch with no live control in a repository is a silent search too,** which is why the tools under `tools/` name the branches their own recipes cannot exercise there.
  - **So is reading a file out of an archive:** `tar xzOf PKG.tar.gz DIR/File.hs | grep -c NAME` prints 0 just as readily for a mistyped in-archive path as for an absent name, so grep something known to be in that file first.
- **Never push, or open/force-update a PR, without an explicit go-ahead.** Permission to make a change is not permission to publish it; `~/.claude/hooks/publish-guard.py` makes the harness ask before a command that pushes or writes to GitHub.
- **Drafting GitHub-bound texts.**
  - One file per destination (issue, its design comment, PR description, upstream PR), staged in `docs/`, posted or not.
  - Keep the *design* implementation-ignorant and put measured results in the PR description.
  - Deliberate overlap between files is fine, to make each self-contained.
  - Don't attribute design intent to code that is merely generic ("assumes irregular indexing"): state observed granularity and cost, not motives.
  - Prefer reference-style markdown links to keep the prose readable.
  - Wrapping is per destination. GitHub renders single newlines as hard `<br>` in issue/PR/comment *bodies*, though not in rendered `.md` files. So a draft meant to be pasted into an issue body, PR description or comment is kept *unwrapped*, one long line per paragraph, `wrap80 --unwrap -i` being what puts it in that form, and is never re-wrapped to 80 columns: a blank line between paragraphs, and tables, code fences, list items, reference-link definitions and `Co-Authored-By` trailers each still on their own line. A doc read as a repo file (e.g. README, committed notes) keeps that file's normal wrapping instead.
- **Links that cite source code, in GitHub-bound texts and the reference documents, must be GitHub permalinks pinned to a commit hash that is on `master`** (`...blob/<commit>/....hs#L12-L34`). Branch-name and unpinned links drift or die when branches move, while a master hash survives rebases and stays verifiable. The citation checker validates such a permalink against the pinned commit and then requires that commit to be an ancestor of `origin/master`: `git show` resolves an unpushed or squashed-away commit from the local object database just as readily, an unpushed commit's link 404s for everyone else, and a rebased-away one's may still resolve. Deliberately-living whole-file links (e.g. the README's `blob/master` pointers) are outside the rule, as are links to foreign repos.
- **A tracked file or a commit message cites no untracked file for what it says, unless Mikolaj approves the mention:** a scratch script or table, a plan, a handoff, a build tree. A clone has none of them and a cleanup can delete them, so the citation comes to point at nothing. State what the text needs from the file, or cite a tracked or published home; naming `/tmp/claude-1000` as the place to write scratch files cites nothing.
- **Name a filed GHC issue by its number, never by the local file that drafted it,** so that a reader follows the reference rather than searching for it (ruled 2026-09-17). `docs/ghc-issue-linear-regalloc-order.md` is a path in this repo, meaningless to a reader anywhere else, and to upstream most of all: the file stays as the filed record, named as a file where a reader should open one and never standing in for the issue. This binds every repo's documents, which reach those files by a path that resolves only in `~/slop`.
  - **In every `.md` file but a body bound for that tracker:** `GHC [#27742](https://gitlab.haskell.org/ghc/ghc/-/work_items/27742)`.
  - **Where a link cannot render (a code comment, a code block inside a document):** the bare URL in place of the number, though a comment in GHC's own source may keep GHC's `#27742` style.
  - **In a commit message and in chat:** `GHC #27742`.
  - **Only inside that tracker-bound body:** a bare `#27742`, which is the one place it autolinks.
  - **The `GHC` is what separates it from horde-ad's own `#123`,** so it is required wherever the surrounding text has not already established which tracker is meant. A first mention carries the full form and later ones in the same document may shorten to the number, adjectivally included.
  - **Two other spellings stay and are exceptions rather than drift:** the header line of a `docs/ghc-issue-*.md`, which names its own work item and its siblings' in the tracker's own noun and sits above the filed body rather than in it; and a third-party item in a sentence that has already said which tracker it is on. What no exception covers is a bare filename standing where the issue belongs.
- **State mathematical properties in the code's surface notation, not abstract math** (in docs and comments alike). Write the gather/scatter adjoint law as `sdot0 (sgather x f) y == sdot0 x (sscatter y f)`, not `<gather x, y> = <x, scatter y>`: keep the index function `f` explicit rather than hidden in the operator name, and put quantifiers first (*for all `f`, `x`, `y`*). It reads in the vocabulary of the code and keeps the shapes checkable.

## Sandboxing on the dev machine (outer wrapper + inner sandbox)

Claude Code sessions on Mikolaj's machine run inside an outer bwrap sandbox wrapper (PID 1 is `bwrap`), beyond Claude Code's own (inner) sandbox. Sessions start in `~/slop`, which holds the repositories worked on but `~/.claude`, so a sandboxed write lands anywhere in them. What follows about writing outside the working directory and about sibling checkouts bites on an edit to `~/.claude`, on a repository outside `~/slop` and on the read-only paths the first bullet names, every repository's `.git/config` among them; the inner sandbox's placeholders land in `~/slop`'s own root rather than a repository's. Each bullet gives the symptom and what to do; how it was measured is in `docs/session-machine-facts.md`.

- **Run `git` writes, `gpg` and SSH pushes unsandboxed:** the inner sandbox mounts `.git/config` and `~/.gnupg` read-only. Sandboxed, `git checkout -b` / `branch -f` fail to lock the config, though the ref often moves anyway, so verify refs afterwards. GPG signing (`commit.gpgsign` is on) fails sandboxed and works unsandboxed, so never fall back to `--no-gpg-sign`.
  - **A sandboxed command may write `~/.cabal`,** which `sandbox.filesystem.allowWrite` in `~/.claude/settings.json` names.
  - **The inner sandbox's network filter refuses every host no settings source allows,** and the same file's `sandbox.network.allowedDomains` allows only GitHub's hosts, GHC's GitLab and Hackage. A call needing any other host lists it in the Bash call's `allowed_domains` or runs unsandboxed.
- **Anything outside the working directory refuses a *sandboxed* Bash write and accepts an unsandboxed one,** the read-only HOME mounts and the sibling checkouts alike; the Write and Edit tools reach both regardless. So there are always two routes: Edit for a few lines, an unsandboxed `python3` splice for anything structural, a move otherwise shipping the block twice through Edit and costing tens of thousands of tokens where a script costs hundreds. `Read-only file system` from a sandboxed script does not mean that Bash cannot write there at all.
  - **A verdict about what any mount permits is the sandbox's unless it was taken unsandboxed.** A path the inner sandbox will not let you write is reported `ro` by a sandboxed `mount` or `findmnt` and `rw` by an unsandboxed one. Sandboxed, `findmnt -T` names the target twice for a path you may write and once, `ro`, for one you may not, which is the cheapest sandboxed test of whether a write will land; but a checkout inside `~/slop` is shown once, `ro`, and takes the write all the same.
- **A blocked write runs nothing at all, and under a typed `&` leaves the command's fate unreadable, which is why a session does not type one.** A simple command's redirections are checked before exec, so `cmd > blocked.log` and `nohup cmd > blocked.log` report the failure and run nothing, the command's own side effects included. A pipeline fails only at its consumer, so `cmd | tee blocked.log` reports the error and `cmd` keeps going; backgrounded with a bare `&` that survivor is detached and invisible. The harness's own background mode reports the job's exit whatever the redirect did, and a pipeline whose consumer died still shows as running.
- **Paths the wrapper blocks report "No such file or directory", not "Permission denied".** If a path outside the repo seems missing, especially one documented as expected, like horde-ad's `../ox-arrays` sibling checkout, suspect the wrapper rather than recording the path as absent. `dangerouslyDisableSandbox` bypasses only the inner sandbox, never the wrapper. `tools/check-doc-refs.py` resolves sibling checkouts when present and stops (exit 2) when one is not, so a BLOCKED run means the check did not happen, not that it passed.
  - **A path created under an unmounted parent succeeds and is invisible outside.** `mkdir ~/r/orthotope-pr` works, reads back, builds, and does not exist for Mikolaj. `git worktree add` to such a path puts the registration and the commits in the mounted `.git`, where they are real and survive, while the working tree is not there at all, and git then refuses to check that branch out anywhere. Prefer a path inside a mounted checkout, and where one is not available say what was written and where rather than reporting a directory delivered.
- **Where a sibling checkout and the released version it tracks disagree, the checkout wins.** It is ahead of the release and actively worked on, not stale, so read it for what upstream *is*. The cabal store provides what the checkout cannot: what to read when the wrapper hides the mount, and whether a version-sensitive name a document pins is really in the release the build plan resolves. A note resting on upstream code the checkout has since changed says so, and names what to re-measure when that work lands.
- **The wrapper mounts a fixed set of HOME paths, curated per path rather than per directory, plus whatever repo checkouts it was launched with, skipping in silence any that do not exist.** The fixed part can be relied on; the checkouts vary from session to session, so verify a sibling at the moment it matters rather than inferring it from habit. That an entry is visible says nothing about how much of its contents is: `~/.ssh` carries public material only.
  - **Measure free space on a checkout, `df ~/slop`, not on `/home`.** What of HOME the wrapper does not mount sits on its root tmpfs, `/home` itself included, so `df /home` reports that tmpfs and not the disk.
- **Sandboxed `ls` shows eleven dotfiles in the working directory that are not on the real filesystem: ignore them, and verify with an unsandboxed command before deleting any.** They are `.bashrc`, `.gitconfig`, `.gitmodules`, `.mcp.json`, `.profile`, `.bash_profile`, `.zshrc`, `.zprofile`, `.ripgreprc`, `.idea` and `.vscode`. The inner sandbox bind-mounts `/dev/null` over these names in the directory it was launched in, once per Bash call, and `~/slop`'s `.gitignore` keeps them, with the `.claude/` placeholders, out of `git status`. HOME is not remapped to the repo root, whatever the names suggest. A name of the eleven that a repository really carries appears empty rather than missing.
  - **A sandboxed `rm -rf` of a checkout below stops at its `.gitmodules` with *Device or resource busy*:** remove that file unsandboxed by name, then `rmdir` what is left.
  - **A backticked name of the eleven in a document makes `tools/check-doc-refs.py` resolve it from a sandboxed session rooted here and fail it from any other seat,** until an entry in `tools/doc-refs-allow.txt` settles the answer everywhere, as one does for `.mcp.json` in this file.
  - **Add no real `.mcp.json` here and no project `sandbox` block.** After each Bash call Claude Code reloads every settings source. The reload reads `.mcp.json` at length zero, so a real one would lose its servers mid-session, and a project `sandbox` block would give the reload `enableWeakerNestedSandbox` to lose.
- **The inner sandbox is in its own PID namespace, so `ps` there lists only the session's own processes and `kill -0 <pid>` is not a liveness test.** It fails for a process that is running fine, and an `until ! kill -0 ...` waiter therefore returns at once. Poll unsandboxed, or watch the thing's output file rather than its pid. A file whose creation the sandbox blocked stays absent whether or not the process is running: there only the unsandboxed process list settles it.
- **System state under wrapper-hidden paths cannot be inspected from inside a session:** such diagnosis must be done by Mikolaj in a plain terminal. Most of `/etc` is in that class, the wrapper carrying `resolv.conf`, `hosts`, `ssl`, `passwd`, `group`, `alternatives` and `fonts` and no more, so the next `/etc` path to come back missing is predictable.
- The nested inner sandbox works only because three things hold; if sandboxed commands start failing at startup, check these first:
  - the Ubuntu AppArmor userns restriction is off (`kernel.apparmor_restrict_unprivileged_userns=0`, no `bwrap-userns-restrict` profile);
  - the wrapper mounts the repo read-write;
  - `enableWeakerNestedSandbox: true` is in effect, inherited from the `sandbox` block of the user-level `~/.claude/settings.json` (a project `sandbox` block wholesale replaces the user-level one, settings objects not deep-merging, so a project that defines one must repeat the flag).

## Git and GitHub in sessions

- **Run `gh` unsandboxed, alongside `git` writes and `gpg`.** Sandboxed it degrades rather than fails, which is the trap: its token is in the keyring, out of the inner sandbox's reach, so it proceeds unauthenticated, at 60 requests an hour and with 403 where a request needs rights. The network itself is there; `gh auth status` names the missing credential outright.
  - **Read GHC's tracker through `glab`, never through `curl` with a pasted token:** `glab api 'projects/ghc%2Fghc/issues?search=...&state=all'`, `glab issue list -R ghc/ghc --search ...`. Its token sits in a readable config file, so it works sandboxed too, but only for the host named by `GITLAB_HOST` (gitlab.haskell.org here); `glab auth status` lists gitlab.com alone even while the other host's credential is present and working.
- `git status --short` is colourised even through a pipe (the bytes are `^[[31m??^[[m path`), so `grep '^??'` silently matches nothing. Use `git status --porcelain`, which is defined as machine-readable and is never colourised.
- **Park a file by copying it aside, not by stashing it.** A `git stash pop` chained after a `git stash push -- <path>` is a trap, because the push can succeed having saved nothing: given a pathspec with no local changes it prints "No local changes to save" and exits 0, so the pop then takes the *top of the stash stack* (hundreds deep in horde-ad, holding parked branch work), restores that into the tree and drops the entry.
- **Commits should be clean and logical, not a diary of the work.** File-partition them and order them so exports precede uses.
  - **Fold a follow-up into the commit where its subject is logically born,** rather than adding "add then move" churn: a correction to what you wrote an hour ago as much as a refactor, a document as much as code, and one `git commit --amend` for as long as that commit is not pushed to master branch. A second commit instead strands the first one's *message*, which goes on asserting whatever the fix retracted.
  - **Rewrite history without `rebase -i` or `add -i`,** tool commands running without a TTY, so that an editor or a prompt loop hangs: `git reset --mixed <base>` and a re-`add`/`commit` per file group, reusing messages via `git commit -C <hash>` / `-F <file>`.
  - **Amending HEAD costs one `--amend`,** and squashing a follow-up into it a `git reset --soft HEAD~1` first.
  - **A non-HEAD commit is the expensive case.** Edits that replace text in files the commit already has, up to any later commit deleting that text, go through `tools/rewrite-fold.py`, which rebuilds the branch tree by tree without conflicts, rewords commits where asked, and prints the new tip for `tools/rewrite-check.py` to check before a guarded reset moves the branch. Anything else is saved as a patch, `git reset --hard <target>` (spares untracked files), applied and `--amend`ed, and the successors `git cherry-pick`ed (conflict-free when they don't touch the amended files). Update recorded hashes either way.
- **Name the paths on every `git add`, and read the diffstat of the commit you just made.** The repo root accumulates many untracked scratch files (`log*`, `*.prof`, `cabal.project.local.bkp*`, `.emacs.desktop*`, etc.): leave them alone and never `git add` them wholesale, `-A` over a directory taking every one of them. Nothing but the diffstat shows such a commit: `git status` then reports clean, the files having been absorbed.

## Build and shell tooling in sessions

- **The GHC to use by default is no released version but `~/slop/ghc/_build/stage1/bin/ghc`, built from the branch `for-review` of `ghc/`:** the NCG series of `for-review-master`, pushed as `wip/T27981-ncg-mystery-box`, on the branch `merged-mrs`, also pushed to [Mikolaj/vibed-ghc-fixes](https://gitlab.haskell.org/Mikolaj/vibed-ghc-fixes/-/tree/merged-mrs), which is GHC master at `3d326d7d28` plus merge requests and fixes. `docs/default-ghc.md` lists the issues it fixes and the merge requests it carries: read that before deciding whether a workaround for a GHC issue is still needed.
  - **It is rebuilt by `hadrian/build -jN --flavour=perf` in `ghc/`.**
  - **Its `ghc --info` names as "Project Git commit id" the commit `./configure` last ran at,** so after a switch of branch without it that id is stale.
- **`pkill -f PATTERN` and `pgrep -f PATTERN` match the issuing shell's own command line, which contains the pattern: take pids from `ps` and `kill` those instead.** `pkill -f` kills the shell that ran it, and the tool call comes back with exit 144 and nothing else, which is not the command failing. Sandboxed calls are spared that, by accident rather than by design: don't lean on it.
  - **The property belongs to any matcher run over your own command line,** so an `until ! pgrep -f PATTERN` or `until ! ps -eo args | grep -q PATTERN` waiter finds its own shell and waits until something kills it. Wait on a file's contents instead.
  - **A pattern the matcher cannot match, `'seq 1 [6]0'`, dodges only its own occurrence:** a kill-then-relaunch script still dies through the literal name in its later launch line, so kill and relaunch go in separate calls.
- `hlint` and `stylish-haskell` are on PATH (via `~/.cabal/bin`) and work in-session, sandboxed included.
- **`grep` and `find` are bash functions that Claude Code writes into its shell snapshot, routing to an embedded ugrep and bfs; `command grep` is the way back to GNU grep, at `/usr/bin/grep`.** A function shadows every PATH entry, and `\grep` does not escape one. The shims are not exported, so a Makefile recipe or a `python3` subprocess already gets the real thing, and the checkers under `tools/` match with Python `re`.
  - **Three of the differences are silent.** A recursive search skips gitignored paths, so a walk over the repo passes over `log*`, `dist-newstyle` and `*.prof`. Binary files are skipped, so `-c` prints nothing and exits 1 where GNU prints a count and exits 0. `-r` output paths lose their leading `./`.
  - **The regex dialect is not one of them:** GNU BRE's `\|` and its siblings behave identically, so an alternation that matches nothing means `-E`, `-P` or `rg`, where `\|` is a literal pipe in any grep.
  - **What is ugrep's own:** `-P` means PCRE2; it can reject a regex outright with `exceeds complexity limits` where GNU grep would run it; and on the one-line-per-paragraph documents here a bounded-repeat alternation can instead run for minutes. Reach for python when a pattern gets involved.
- **A tasty `-p` pattern matches by *containment* and cannot be anchored.** A pattern of nothing but alphanumerics, `.`, `_`, `-` and spaces is taken whole as a literal substring and never parsed (the ordinary form, `-p "4S"`). Anything else goes to the awk grammar, where an ERE token `/foo/` recognizes no special characters either and `$NF` is the test's own name.
  - **To combine several patterns, use that awk-style syntax:** `-p "/foo/ || /bar/"`.
  - **An anchor fails two ways and only one is loud:** `-p "^detSquare"` is rejected, "is not a valid pattern", where `-p "/^detSquare/"` is accepted and silently selects nothing. `-p '$NF == "detSquare9"'` is the exact-match form.
  - **Containment bites silently wherever names are numbered:** `-p "gatherNested1"` selects two tests, `gatherNested1` together with `gatherNested12`, so a filter believed to name one test quietly runs two, and a count taken through it moves for reasons nobody sees.
  - **Mint a marker by listing before the series exists:** the same `--list-tests` reports a count for a marker that does exist, which is what keeps the check from passing vacuously.
- **Criterion (the benchmark suites) filters differently and does *not* accept that syntax: it has no `-p`.** Bare positional args are **prefix** patterns on the full `group/bench` path, and `-m glob`/`-m pattern`/`-m ipattern` switch the match mode (e.g. `--benchmark-options='-m glob "*/S-exec"'` to pick a bench across groups, or a bare `--benchmark-options='cnn-24x24'` prefix).
- **A verification command must not be piped, and must not sit behind `&&` either: redirect to a file and echo `$?`, or put the check in its own call.** A shell pipeline exits with its *last* command's status, so `cabal test CAFlessTest --enable-optimization | tail -40` reports `tail`'s success whatever the run did, and the session harness then reports "exit code 0", which looks exactly like a pass. It bites hardest where warnings are deliberately ignored, as in horde-ad's standing checks: the exit status is then the whole signal, and the pipe is what discards it.
  - **The `&&` chain is the same defect and fails one step earlier:** a status read placed after `&&` does not run at all when something before it fails, so a trailing `||` fallback fires and looks like the verdict. `git commit ... && git log ... && git status ... || echo "(tree clean)"` prints *(tree clean)* with the commit refused. Read the state directly afterwards; a fallback that can print a result for a command that never ran is not a check.
- **GHC emits warnings only on *recompilation*:** a cached, up-to-date build can hide warnings (e.g. `-Wredundant-constraints`) that a full rebuild would surface, so don't infer "no warnings" from a clean second build.
  - **Optimization level hides a second class:** `-Wmissed-specialisations` fires only when the specialiser runs, so a from-scratch `-O0` build reports none of it.
  - **`--ghc-options=-fforce-recomp` does not help:** cabal reports "Up to date" and compiles nothing, since the flag doesn't reach its staleness check. To force a genuine rebuild, build into a fresh `--builddir`, which leaves the existing artifacts alone.
  - **A released GHC's recompilation check misses a change of any setting that carries a *value*,** `-fllvm`, the inliner thresholds and `-fproc-alignment` among them (GHC [#27667](https://gitlab.haskell.org/ghc/ghc/-/work_items/27667), fixed in the default GHC above). So an A/B that toggles one of those measures nothing unless it forces the rebuild.
- **`-keep-s-files` keeps nothing under a build that names `-pgma`:** capture the assembly a shim plans over by wrapping `-pgma` in a script that copies each `.s` argument aside and then runs the shim.
- **`-dumpdir` and `-outputdir` are ignored for a source given by an absolute path, or found through an absolute `-i`: its dumps land beside it** (GHC [#28096](https://gitlab.haskell.org/ghc/ghc/-/work_items/28096)), so two compilers' dumps of one module overwrite each other there. Compile from the source's directory, or add `-ddump-file-prefix=M`, which appends the dot itself. A source in a subdirectory gets its dumps in the same subdirectory of the dump directory, GHC joining that directory with the source's path by `</>`, while `-odir` and `-hidir` place by the module's name.
- **A binary under `dist-newstyle` can silently predate the tree, so check before measuring it.** `cabal build convVjpBench --dry-run` names what it would rebuild and why ("file X changed"), which is the cheap way to know the executable about to be timed is the one the source describes. An edit reverted without a rebuild leaves the binary carrying the reverted code.
- Keep one set of cabal flags across a session: changing flags (e.g. toggling `--enable-optimization` or `--enable-profiling`) forces a full rebuild of the local packages, though each flag set's dependency builds stay cached in the store. Pass such flags on the command line rather than editing `cabal.project.local`.
- **The `/tmp` scratchpad is wiped by every machine restart, and a restart can come unannounced, so put there only what can be regenerated and nothing cites.** A script, a draft, a patch or a result that a note, a finding or a later step names or reruns goes in the repo tree or the work's own directory from the start, with a note to delete it afterwards; binaries just get rebuilt.
  - **So does anything Mikolaj has to run or open himself** (a `! bash foo.sh` script, a diff to review), which the wrapper's tmpfs over `/tmp` also hides from his shell: handing over a scratchpad path yields "this file doesn't exist" and a wasted round trip.
  - **Spell scratch paths out as `/tmp/claude-1000/...` in both seats:** that directory is writable in both. `$TMPDIR` is `/tmp/claude-1000` only under the inner sandbox; an unsandboxed command uses `/tmp`, so a file one seat writes to `$TMPDIR/foo` is missing from the other's.
- Exact dependency sources are always available: unpack `~/.cabal/packages/hackage.haskell.org/<pkg>/<ver>/` matching `dist-newstyle/cache/plan.json`.
- **`.github/workflows/haskell-ci.yml` is generated by `haskell-ci` from the `.cabal` file: regenerate it (`haskell-ci regenerate`) rather than hand-editing.** Anything the generator does not produce belongs in `cabal.haskell-ci`, not in the generated file: a plain field where one covers it (`apt:` for extra system packages, `run-tests:`, ...), and `github-patches:` for a diff reapplied on every regeneration. A hand edit left outside that config is not merely fragile: it disappears *silently* on the next regenerate.
  - **After changing the config, regenerate twice and compare:** a patch that applies cleanly once can double-apply.
- Toggle-based A/B builds: make a rule's guard unsatisfiable (e.g. `sigmaL /= sigmaL`), build and copy the binary aside, restore + rebuild + copy again, then run the two preserved binaries in interleaved pairs (no rebuild between A and B); an edited `Core` module rebuilds in ~10 min.
